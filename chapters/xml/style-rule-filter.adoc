=== Style

Styles contain a set of rendering rules to render data elements provided by a data source. Each style can contain one or more rules for rendering specific features.

.Style attributes
[options="header",cols="m,d,d,d"]
|====================
| Attribute                 | Value | Default | Description
| name | string | | The name a style can be referred by
| comp-op | SVG compositing |  |
| filter-mode | "all", "first" | "all" |
| opacity | float | 1 |
| image-filters-inflate | boolean | false |
| image-filters | string |  |
| direct-image-filters | string |  |
|====================


=== Rule

A style rule filters data elements provided by a data source, and renders the matching elements using one or more symbolizers. Rules can also be limited to specific scale factor ranges only, e.g. to implement different zoom level styles.

.Rule attributes
[options="header",cols="m,d,d,d"]
|====================
| Attribute                 | Value | Default | Description
| name | string | none |
|====================


=== Filter

Filters specify on what data elements a rule should operate, by evaluating expressions. The expression language supports simple comparisons, logic, math, and regular expression matching.

There are also two special filters that do not evaluate expressions but depend on whether other previous filters in the style found a match:

<ElseFilter> matches if no other filter in a style matched so far, so it can be used as a fallback default.

<AlsoFilter> only matches if at least one previous filter in a style matched.

The `<Filter>` tag has no tag attributes.

==== Filter expressions

The filter expression language supports the following constants, operators, and functions. It also allows for referencing data element attributes by putting the attribute name in square brackets `[attribute]` and to change evaluation order by putting expression parts in regular round brackets `(...)`.

===== Operator Precedence

[cols="1,6,2",options="header"]
|===
| Level | Operators | Grouping
| 1 | literals, `+[attribute]+`, `+@variable+`, function calls, `+( … )+` | –
| 2 | unary `-`, unary `{plus}` | –
| 3 | `+*+` `+/+` `+%+` `+.match()+` `+.replace()+` | left to right
| 4 | `{plus}` `-` | left to right
| 5 | `+<+` `lt`, `+<=+` `le`, `+>+` `gt`, `+>=+` `ge` | left to right
| 6 | `+=+` `eq` `is`, `+!=+` `+<>+` `neq` | left to right
| 7 | `not`, `+!+` | –
| 8 | `and` `+&&+`, `or` `+\|\|+` (*same level*) | left to right
|===

Note that these work a bit different to what one may be used to:

* `and`/`or` have the same precedence, evaluated left to right:
  `+true or true and false+` → `+((true or true) and false)+` = false
  (SQL, C and Python would give true).
* `not` binds looser than comparisons: `+not 1 = 2+` → `+not (1=2)+`.
* `+not not true+` is a parse error; use parentheses.
* Comparisons chain as booleans, not as ranges: `+1 < 2 < 3+` → `+((1<2)<3)+`.
* Equality binds looser than `+<+`/`+>+`: `+1 = 1 < 2+` → `+1 = (1<2)+`.

===== User Variables

User variables are referenced by a leading `@` followed by the name; they can be set
when requesting to actually render a styleshet.

With the Python bindings this is done by calling the `render_with_vars()` method
instead of just `render(). Unfortunately this method so far only exists for the
Agg render backend, but not for Cairo Graphics or native SVG backends yet.
